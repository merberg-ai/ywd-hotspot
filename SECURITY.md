# 🔐 Security Policy

[Project README](README.md) · [Installation](docs/INSTALL.md) · [Upgrading](docs/UPGRADING.md) · [Contributing](CONTRIBUTING.md)

YWD-Hotspot controls radio/network services and stores reusable credentials. Treat a deployed hotspot as an appliance, not a disposable static website.

## Current release state

`0.2.0-rc1` is being prepared as the public testing prerelease from the immutable physically proven builder checkpoint. The public artifact is not promoted/published until the exact factory image passes physical smoke testing.

## Network exposure

The normal dashboard uses plain HTTP and is intended for a trusted LAN.

> [!CAUTION]
> **Do not directly expose the dashboard TCP port to the public Internet.**

Remote administration should use an authenticated/encrypted access layer rather than direct dashboard forwarding.

## Public factory-image security

The GitHub prebuilt image is generated by a fail-closed release wrapper. It must contain no operator/builder personalization:

```text
Wi-Fi credentials       none
Callsign/DMR ID          none
BM credentials/API key  none
Dashboard password      none
Imported settings       none
RF autostart             OFF
SSH                      disabled
Builder authorized key  none
```

The release gate validates the source builder profile and generated first-boot payload before the build, validates them again through the actual build path, and refuses release metadata if personalization is detected.

With no saved Wi-Fi, first boot uses the temporary `YWD-Hotspot-XXXX` setup AP. Hotspot configuration then requires the one-time OLED code over the dedicated HTTPS setup service.

## Secrets

YWD-Hotspot separates:

1. BrandMeister Hotspot Security password;
2. BrandMeister API v2 key;
3. local WebUI control password;
4. plugin publisher public trust keys;
5. optional operator SSH credentials.

The BrandMeister API key and reusable passwords remain server-side. Browser JavaScript does not receive them back.

Never post real credentials in GitHub issues, screenshots, terminal pastes, logs, support bundles, or public release artifacts.

Sensitive paths include:

```text
/etc/ywd-hotspot/config.json
/etc/ywd-hotspot/bm-api.key
/etc/ywd-hotspot/web-auth.json
/var/lib/ywd-hotspot/private/
/var/backups/ywd-hotspot/
```

`/etc/ywd-hotspot/build-info.json`, `/etc/ywd-hotspot/mmdvm-runtime.json`, and `/etc/ywd-hotspot/mmdvm-build.json` are intended to contain non-secret provenance/runtime identity only.

## MMDVM runtime variants

YWD Extended applies only the exact pinned/hash-verified YWD extension patch. Stock Upstream applies no patch. Runtime provenance records which variant is installed.

Plugins may require YWD Extended/API/capabilities, but satisfying a requirement does not grant modem ownership or RF TX. A plugin cannot switch the installed MMDVM runtime by itself.

## GitHub update trust boundary

Managed deployments use `/opt/ywd-hotspot/repo`. The updater preserves these protections:

- canonical-origin verification;
- dirty-content refusal;
- candidate staging outside live runtime;
- capability-based required-file validation;
- shell/Python validation;
- protected pre-update backup;
- RF/service-state preservation;
- coherent privileged bridge before dashboard restart;
- plugin quiesce/restore safety;
- managed source advanced only after successful deployment.

Normal application updates do not silently rebuild/switch the MMDVM runtime.

## Web privilege boundary

The WebUI runs as restricted `ywd-hotspot`. Root-required browser actions go through the narrow privileged dispatcher and sudoers policy. The browser must not gain arbitrary shell execution or direct write access to generated MMDVM/DMRGateway INIs.

## Plugin trust boundary

Executable service/UI plugins require trusted Ed25519 signatures. Private signing keys never belong in the hotspot, Git repository, or settings backup. Plugin capability/requirement declarations are interpreted by trusted core and do not allow custom shell/package-install commands.

## Diagnostics

Prefer:

```bash
sudo ywd-hotspotctl diagnostics
```

Sanitized diagnostics are designed to redact reusable credentials, but always review a bundle before publishing it. Never upload raw protected config/update backups.

## Reporting a security issue

Do not open a public issue containing exploit details together with working credentials/private deployment data. If GitHub private security reporting is available, use it; otherwise request a private contact path without including secrets.

## Changes requiring extra scrutiny

- broader sudo permissions;
- user-controlled shell execution;
- secrets exposed to browser JavaScript;
- weakened update/repository validation;
- browser direct edits to generated INIs;
- public-Internet exposure features;
- plugin RF/modem ownership;
- MMDVM pin/patch/runtime-selection changes;
- factory-image changes that could embed credentials or unexpectedly enable RF.
